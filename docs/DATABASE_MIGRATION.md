## Translation rules applied
| MySQL | PostgreSQL |
|---|---|
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` (190 columns; sequences resynced after seed in `015`) |
| `TINYINT/SMALLINT/INT/BIGINT UNSIGNED` | domains `u8/u16/u32/u64` (range-checked); identity columns use plain `smallint/integer/bigint` wide enough for the unsigned range |
| `ENUM(...)` | `text` + named `CHECK (col IN (...))`, named `enum_<col>` (119) |
| `BOOLEAN` | `boolean` |
| `TIMESTAMP`, `DATETIME` | `timestamptz` |
| `YEAR` | domain `u_year` (1901–2155) |
| `JSON` | `jsonb` |
| `VARBINARY` | `bytea` |
| `ON UPDATE CURRENT_TIMESTAMP` | `BEFORE UPDATE` trigger `sims_touch_updated_at()` (bumps only if the row changed, as MySQL does) |
| `GENERATED ALWAYS AS (...) STORED` | same (13 columns; nullable-unique "current primary" keys behave identically) |
| `INSERT IGNORE` | `ON CONFLICT DO NOTHING` |
| `REGEXP` | `~` |
| `DATEDIFF`, `TIMESTAMPDIFF`, `IFNULL`, `DATE()` | `date - date`, `age()`-based expression, `COALESCE`, `CAST(.. AS date)` |
| triggers (`SIGNAL SQLSTATE '45000'`, `<=>`) | PL/pgSQL, `RAISE EXCEPTION … ERRCODE '45000'`, `IS NOT DISTINCT FROM`; row locks (`FOR UPDATE`) kept |

## Deliberate divergences and caveats
1. **BIGINT UNSIGNED** is stored as non-negative `bigint`; values > 2^63−1 cannot be stored. None are expected.
2. **Timestamps**: MySQL `DATETIME` was zone-less (the source assumes UTC sessions); it is now `timestamptz`.
3. **`ALTER … ADD COLUMN … AFTER`**: column order is not preserved for the 3 added `file_object` columns.
4. **Prefix indexes** (`col(191)`, 3 indexes: `idx_journal_publication_title`, `idx_journal_name`, `idx_external_org_name`) became full-column indexes.
5. **Collation**: MySQL `utf8mb4_0900_ai_ci` compares case- and accent-insensitively, including for UNIQUE keys. The Postgres tables are currently **case-sensitive**. This is an open decision (B5 in the audit; `citext` recommended). Until decided, duplicate codes differing only in case can be inserted.
6. **JSON → jsonb** does not preserve key order or duplicate keys.
7. **`TIMESTAMPDIFF(MONTH/YEAR)`** in `v_employee_previous_experience` is approximated with `age()`; month-end edge cases may differ from MySQL. Not verified.
8. **Trigger structure**: the 3 `fee_item` and 3 `payment_allocation` after-triggers and the paired before-insert/update triggers share PL/pgSQL functions, but each of the 16 original trigger names exists.
9. **Additions that are not in the source**: 6 domains, 37 `updated_at` triggers, identity resync (`015`), RLS-on-everything baseline (`016`), `security_invoker` on views, `SET search_path` on trigger functions.

## Source defects found
- **SD-1** `file_object`: the `ALTER TABLE file_object ADD COLUMN …` (source line 3463) re-adds `stored_file_name`, `file_extension`, `storage_url`, `is_encrypted`, which `CREATE TABLE file_object` already defines. MySQL would abort with "Duplicate column name" (the header says to run without `--force`). The migration adds only the three genuinely new columns (`encryption_key_reference`, `virus_scan_status`, `virus_scanned_at`). Needs owner confirmation.
- **SD-2** `user_account.password_hash` exists in the source. With Supabase Auth, credentials live in `auth.users`; this column will not be used for authentication (identity-map design in the RBAC phase).

The first reconciliation draft listed `file_object` as missing `encryption_key_reference`, `virus_scan_status`, `virus_scanned_at`.
